# Database and backup

SQLite (`data/koreograf.db`, WAL, one writer) stays the default. An empty `KOREOGRAF_DATABASE_URL`, or a value of `sqlite:`, means that file. A `postgres://` or `postgresql://` URL selects PostgreSQL instead; both engines use the same schema and serve the same API and UI. The same backup works on both engines: it is always one SQLite file plus the key, not a raw copy of the data directory, so an archive from either engine restores into either engine. [PostgreSQL](postgresql.md) covers the URL, password file, TLS options, and the move from SQLite. [Configuration](configuration.md#postgresql) lists the variables.

An administrator opens **Backup** in the sidebar. In the German UI the link is **Sicherung**.

- **Download** writes `koreograf-backup.zip`. Inside are `manifest.json`, a consistent database (`koreograf.db`, copied through the SQLite backup API on SQLite and exported row by row on PostgreSQL), and `secret.key`. Without the key, credentials cannot be read after a restore. The manifest keeps a versioned `format`, the engine, the creating version, and `includes`/`omits` lists.
- **Include OpenTofu state** is off by default. When it is on, the zip also contains `cache/<team>/tofu-state/<template>/`. That state can contain secrets such as provider values or resource attributes. A remote backend is still the better setup when state must leave the host.
- **Left out** are the other parts of the cache, git checkouts, and job directories. The next run fetches collections and roles again, and git projects are cloned again. A template that does not update on launch needs a project sync after a restore. Projects that use a local path need that same path, or a matching `KOREOGRAF_PROJECT_ROOTS` entry, on the target machine.
- **Restore** replaces the installation on SQLite or PostgreSQL. Finish running jobs first. The request sends the zip body and the header `X-Restore-Confirm: ERSETZEN`. A new sign-in is required afterwards. On PostgreSQL the replacement runs in one transaction and rolls back when a row cannot be written. The previous installation stays as `restore-previous.zip` in the data directory (mode `0600`) and can be restored the same way on either engine. An unknown manifest `format` is refused before anything is replaced. Restore replaces the OpenTofu state directories under `cache/<team>/tofu-state/` only when the backup includes state; a backup without state leaves the existing state untouched.
- **Restore on start** uses `KOREOGRAF_RESTORE_FROM=/restore/koreograf-backup.zip` when the data directory is empty. It restores before the port opens, logs the result, and renames the file to `koreograf-backup.zip.applied` so a restart does not apply it twice; mount that directory writable. A non-empty data directory ignores the variable with a warning and overwrites nothing. The API keeps the confirm header.
- **Import an existing data directory** uses `KOREOGRAF_IMPORT_FROM=/import` on the first start with an empty data directory. Koreograf validates `koreograf.db` and `secret.key`, copies the database with the SQLite backup API so an active WAL file stays consistent, copies the key and the OpenTofu state, and writes a report. A cleanly stopped installation without a WAL file is read through a read-only immutable URI, so both a running and a stopped old service work. The import writes into a hidden staging directory and moves it into place only after the database, key, state, and report are complete; a failed run leaves the data directory empty and the next start retries. `KOREOGRAF_IMPORT_CACHE=1` also copies the rest of the cache. The source directory is only read; nothing is written to it. A non-empty data directory ignores the variable.
- The import refuses a database with a schema newer than this build. Older databases are migrated when they can be read.
- Stored path-project sources and `KOREOGRAF_PROJECT_ROOTS` that do not exist in the container are listed in the log and on the Overview page as paths that need a mount or a change. `KOREOGRAF_PATH_MAP=/home/user/projects=/projects` rewrites matching path-project sources once during the import and stores the mapping in the database. There is no guessing; a path that is not in the map stays unchanged.
- Files written into the data directory belong to uid 10001 when the container starts as root through the entrypoint. In the published image the server itself already runs as uid 10001.
- The file is secret: it contains users, hooks, and the key for every credential. The upload and total backup limit is 256 MiB; a download that would exceed it fails instead of producing a backup that restore refuses.

`GET /api/admin/backup` and `POST /api/admin/backup` are limited to the local administrator. `GET /api/admin/backup?tofu_state=true` includes the OpenTofu state.

## Schema versions and upgrades

Koreograf applies schema changes from numbered migrations in `migrations/sqlite/` and `migrations/postgres/`. The files are embedded into the binary, applied in order, and each one runs in a transaction together with its version update. SQLite stores the version in `PRAGMA user_version`; PostgreSQL stores it in `schema_meta` under `schema_version`.

Version `1` is the numbered baseline (`0001_baseline.sql`), which is the schema of the 0.1.0-alpha releases. A fresh database starts at `0` and applies the baseline. An existing database that reports version `1` without the numbered baseline marker is recognised as a legacy database: the old idempotent step runs once, the database is stamped with the baseline version, and later starts skip it. A database with a version newer than the running build refuses to start, so an older binary cannot damage newer data. A migration that fails rolls back, and the stored version stays unchanged; the next start retries it.

Backups and imports follow the same rule. An older backup is migrated after it is unpacked; a backup from a newer build is refused before anything is replaced. `koreograf db migrate` applies the PostgreSQL migrations to the empty target before copying, so the target ends on the same schema version as the SQLite source. `tests/upgrade.rs` opens a database created by 0.1.0-alpha.10 on both engines and checks that users, teams, templates, and jobs survive the upgrade.

## Copy SQLite data to PostgreSQL

The full guide is [PostgreSQL](postgresql.md#move-an-existing-sqlite-installation). `koreograf db migrate --to postgres://…` and **Settings → Database** copy the current SQLite database into an empty PostgreSQL database. The CLI needs the server stopped; the UI runs the same checks and copy in maintenance mode. Both open `koreograf.db` read-only, so the SQLite file is never changed.

Before writing, it checks that the target is reachable with the existing TLS settings (`KOREOGRAF_DATABASE_CA_FILE`, `KOREOGRAF_DATABASE_PASSWORD_FILE`, and `sslmode`), that the user may create tables, that the server is PostgreSQL 13 or newer, that the SQLite schema is current, and that every table in the target schema is empty. A target that only has the schema with zero rows is accepted.

The copy keeps every primary key and copies encrypted secrets as stored. `secret.key` stays in the data directory and is not written to PostgreSQL. Row counts are checked per table, identity sequences are reset, and the schema version is recorded in the same transaction. On failure the transaction rolls back and the command says the target can be reused; an empty schema left by the failed run is fine for the next attempt. Run the current build once against the SQLite file first if it reports an older schema.

On success the command prints the `KOREOGRAF_DATABASE_URL` value without the password, then restart Koreograf with it. Keep the password in `KOREOGRAF_DATABASE_PASSWORD_FILE`. To roll back, stop the server, set `KOREOGRAF_DATABASE_URL` back to empty, and start again from the unchanged `koreograf.db`; the PostgreSQL data is no longer used. [PostgreSQL](postgresql.md) shows the per-install switch and verification steps.
