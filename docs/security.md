# Security

The prototype is meant for a trusted network. The Docker socket is root on the host. A mounted `/var/run/docker.sock` lets Koreograf start an image an owner or an operator selected, with mounts and a command that image chose. Anyone who can reach the socket can also start a privileged container and read or change the host. Prefer rootless Podman or rootless Docker, which still limit the host but map the socket to a user. The next step is a socket proxy that allows only the calls Koreograf makes: `version`, `info --format`, `image inspect`, `pull`, `run`, `inspect`, `kill --signal`, and `rm -f`. A proxy still sees those calls as permission to start arbitrary images, so it is not a sandbox. Do not expose the socket over TCP without TLS and authentication. The published image runs as uid 10001. `docker-compose.socket.yml` starts the entrypoint as root with only `CHOWN`, `DAC_OVERRIDE`, `SETUID`, and `SETGID`, joins the socket's group, and drops to uid 10001 before the server starts. The base Compose file keeps uid 10001 and needs the socket's gid from the runtime. The job container does not receive the socket. It does see the decrypted credential files of that job. The Helm chart keeps uid 10001 with the socket's gid in `supplementalGroups`. `data/secret.key` decrypts every credential and the saved directory and proxy passwords. Copying that file, the SQLite database, or `koreograf-backup.zip` exposes them. `KOREOGRAF_LDAP_TLS_INSECURE` and an open port without TLS do not belong on the internet. Company CAs come from the read-only `/etc/koreograf/ca` mount and are added to the public roots. A missing or empty directory leaves trust unchanged, and an unreadable or non-PEM file stops the start instead of turning checks off. Turning checks off writes a warning, and a NetBox source that does so shows a badge. Responses set `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and a content security policy. Pages set layout with style attributes, so that policy allows those attributes and still blocks inline scripts. `KOREOGRAF_HSTS=true` adds `Strict-Transport-Security`. Leave it off when the process is reached over plain HTTP. `KOREOGRAF_COOKIE_SECURE` defaults to `auto` and does not mark the session cookie `Secure` until a trusted proxy reports HTTPS, or until the flag is `true`.

`POST /mcp` uses the same bind address and bearer tokens as the HTTP API. A cookie alone is not accepted, so a browser session cannot reach it. A missing or unknown token answers 401. `KOREOGRAF_MCP=0` disables the route with 404. The tools can start jobs that the token's role can already start, so treat a personal API token like an operator credential and revoke it under `/api/me/tokens` when it is no longer needed.

The assistant is off until an administrator enables it under **Settings → Assistant** or with `KOREOGRAF_LLM=1`. Its tool list is the MCP tool set, and every call runs through the same API with the signed-in account's session or personal API token. A viewer therefore cannot launch, cancel, sync, or relaunch through chat; the chat routes answer 403 before the call. With the flag off, `GET /api/assistant` and `POST /api/assistant/chat` answer 404 and the navigation has no chat entry. The saved API key is encrypted with `data/secret.key`, masked like the LDAP bind password, and never returned by `GET /api/settings`. It is never logged. The chat transcript stays in the browser session; the server keeps a pending write for ten minutes in memory so a confirmation can run it.

Enabling a cloud provider sends every prompt, tool result, and explanation request to that endpoint. Treat that endpoint as a recipient of job metadata and redacted output. Prefer a local Ollama, or an OpenAI-compatible gateway inside the same network, for an air-gapped or otherwise isolated install. The proxy settings apply to the request.

Before anything reaches the model, Koreograf redacts it. Credential secrets, SCM tokens, vault passwords, LDAP and proxy passwords, the assistant API key, the caller's session or API token, and every `extra_vars` value are removed. Job output and JSON answers pass through the shared git-credential and `password=`/`token=` masking, plus masks for bearer headers, private key blocks, Ansible Vault blocks, and secret-shaped tokens such as `sk-`, `ghp_`, and `glpat-` values. A known stored secret is replaced wherever it appears. Job metadata and output for **Explain this failure** take the same path, and long output is truncated after redaction. Assistant tool calls are logged with the account, tool name, action target, and outcome; arguments, prompts, output, and secrets are not logged.

The assistant writes are `launch_template`, `launch_workflow`, `cancel_job`, `relaunch_job`, `sync_project`, and `sync_inventory`. Each one returns a confirmation card that names the object, and nothing changes until the signed-in user confirms. Cancelling the card drops the pending action. The confirm route repeats the team role check, so a permission change between the card and the click still refuses the write.

Local jobs run as the server user. The container image has no local mode and no local tools. Outside the image, `KOREOGRAF_LOCAL_RUNNER_FOR` defaults to `admins`, so an operator or an anonymous webhook cannot start one. The template, project, inventory, and workflow that supply the command must have been saved by an administrator. Relaunch checks the stored parameters, not only the template as it looks now. The job process does not inherit the server environment. Ansible extra vars are written as unsafe YAML, so a webhook value is not evaluated as a template. Decrypted credential files are removed when the job ends and again on the next start. A container cannot mount the data directory.

Path projects and `file://` clones cannot use the data directory or a system directory such as `/etc`. The examples directory is always an allowed root. Any other directory has to be listed in `KOREOGRAF_PROJECT_ROOTS`, and a saved path outside those roots does not run. See [Configuration](configuration.md).

LDAP sign-in does not take over a local account that already uses the same username. A team bound to a group DN matches that directory entry. A CN binding matches the CN under the search base.

If an operator who should not have been trusted could start local jobs, create new credentials and retire the old ones, `secret.key` decrypts every stored secret, and a backup zip from that period contains the same key.

How to report a vulnerability is in [SECURITY.md](../SECURITY.md).
